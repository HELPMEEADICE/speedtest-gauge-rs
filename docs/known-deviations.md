# 已知偏差（known deviations）

本文逐条记录**本移植与原实现（[speedtest-gauge-svg](https://github.com/HELPMEEADICE/speedtest-gauge-svg)
+ Chromium/SVG 渲染）之间的可观测差异**：现象 → 量化影响 → 根因机制 → 已尝试的修复与结果 →
是否可接受。

口径：

- 「量化影响」里的数字全部来自本 crate 的实测记录（`docs/visual-targets.md`、`docs/font-metrics.md`、
  `PROBE.md`、`comparison/ref-metrics/*.json`、`examples/shots` 的运行时输出），不是估计。
- 参考基准 = 原站在 Chromium 下的 1144×1144 截图（4 px/uu），见 `docs/reference-inventory.md` §4。
- 验收线：亮弧终点 `|Δ| ≤ 0.2°`、指针渐变 `max|Δ| ≤ 4/255`、刻度文字残差 `≤ 0.5 uu`
  （`docs/visual-targets.md` §6、`examples/shots` 的阈值打印）。
- 本文与 [`module-map.md`](module-map.md) §2「有意偏离」互补：那里记"主动不照抄"，这里记
  "照抄了但没完全一样"。

## ① 字体光栅器不同：FreeType/Chromium vs skrifa/Slint

**现象**：同一份字体文件（`assets/fonts/montserrat.ttf`、`.local-fonts/gaugemono.ttf`），
在 Chromium 与 Slint 里排出来的字，**墨迹宽度与位置差零点几个 uu**。

**量化影响**（`docs/font-metrics.md` §3.1 的 `hmtx` 权威值与 FreeType hinted 实测）：

| 串 | `hmtx` 精确 em | × 字号 = 权威 advance | FreeType `getlength`（hinted 整数网格） | 差 |
|---|---|---:|---:|---:|
| `Mbps` @14 | 2.866 | **40.12 uu** | 41.0 px | +0.88 uu（+2.2%） |
| `1000` @14 | 2.429 | 34.01 uu | 36.0 px | +1.99 uu（+5.9%） |
| `0` @14 | 0.679 | 9.51 uu | 10.0 px | +0.49 uu |
| `4` @14 | 0.689 | 9.65 uu | 11.0 px | +1.35 uu |

**根因机制**：14 ppem 太小，字体自带 `fpgm`/`prep` 字节码 ⇒ FreeType 在 14 px 下把每个字形推进
**拟合到整数网格**（量化上界 ±0.5 px/字形）；Chromium 默认开 subpixel positioning，不做这层
整数吸附。Slint 侧走 skrifa（同样无 subpixel positioning，但取整策略与 FreeType 不同），
于是三者是**三种不同的取整**，而不是"谁对谁错"。

**已尝试的修复与结果**：

1. 用 `hmtx` 权威 em 手算期望宽度 —— 只能当**下界**参考，无法让渲染器听你的；
2. 选 14 uu 以上的字号 → 会破坏与 `GEO.label_font_size = 14` 的一致，放弃；
3. 最终做法：**不追字形宽度，追墨迹中心**（见 ②），并把 `docs/font-metrics.md` 的 `hmtx` 列
   定为"Rust 侧做布局估算时用的权威列"（源码注释原话：`Rust 侧无字体估算请用 单位/1000 那一列`）。

**可接受**：是。字形覆盖率已核（`0123456789Mbps` 全命中，`docs/font-metrics.md` §3.2），
剩余差异是**渲染器取整策略**造成的亚像素级位移，不影响任何读数的可读性与对齐锚点。

## ② `dominant-baseline` 与 Slint 行盒模型差（已补偿到 0.13 uu）

**现象**：原实现用 `text-anchor: middle` + `dominant-baseline: central` 让 `(x, y)` 成为**文字视觉
中心**；Slint 的 `Text` 按**元素包围盒 + 行盒**对齐，同样的 `y` 会整体偏低。

**量化影响**：

- 补偿前：9 个刻度标签的 ink 中心普遍比锚点**低 1.1–1.25 uu**（`docs/visual-targets.md` §4 的
  实测列，例如 `5`：锚点 `47.86, 161.85`、实测 `47.80, 160.60` ⇒ Δ `(−0.06, −1.25)`）。
- 补偿：`label-dy = -1.375`（`ui/speed-gauge.slint:93,96`，组件属性，可在宿主侧覆盖）。
- 补偿后残差：`1.375 − 1.25 = 0.125 ≈ **0.13 uu**`（方向与补偿相反，即轻微过冲）。

**根因机制**：三件事叠在一起——

1. SVG 的 `dominant-baseline: central` 对齐的是**字面中心**（em box 中部）；
2. Slint 的 `Text` 对齐的是**行盒**（`font-size` × 行高比，且行高由渲染器给的上升/下降量决定）；
3. 两者对 Montserrat 的 ascent/descent 取值不同 ⇒ 恒定偏移，与字号成线性。

**已尝试的修复与结果**：

1. 只调 `y`（逐个标签偏移）→ 能对齐但**与源码结构脱钩**（源码是"极坐标算落点"，逐个偏移就
   等于把几何表抄死），放弃；
2. 依赖 `vertical-alignment: center` 的自适应 → 那是元素盒居中，不是字面居中，偏得更多；
3. 采用**单一全局常量** `label-dy`（默认 −1.375，宿主可调），把残差压到 0.13 uu < 验收线 0.5 uu。

**可接受**：是。0.13 uu 在 1144 图上 = 0.52 px，落在抗锯齿边缘内。

## ③ 参考图自身就有 0.5 uu 的读数散布

**现象**：拿同一张参考 PNG，用不同**扫描角**量同一个几何量，读数会变。

**量化影响**（`docs/visual-targets.md` §1，径向扫描 @ r=130，1144×1144 / 4 px per uu）：

| 量 | 理论值 | 实测范围 | 散布 |
|---|---:|---|---:|
| 圆环内半径 | 118.5 | 118.3 … 118.8 | **0.5 uu** |
| 圆环外半径 | 141.5 | 141.55 … 141.7 | 0.15 uu |
| 环宽 | 23.0 | 23.0 … 23.2 | 0.2 uu |

且 `docs/visual-targets.md` §1 明确写了：−60° / +60° 是最干净的扫描角，`0°` / `±100°` 会先打到
刻度字（r≈93–104），那些角度的内半径读数**无意义**。

**根因机制**：抗锯齿把理想边界变成 1 px 宽的**覆盖率渐变带**，"边界"取决于你用什么阈值判定
（50% 覆盖率？非背景色？luma > 60？）。阈值一变，读数就沿着那条渐变带滑动。

**已尝试的修复与结果**：统一定义"非轨道色且覆盖率 > 50%"为边界，并在两条最干净的扫描角
（±60°）取样；对参考图与本移植的渲染**用同一段测量代码**（`tools/measure_reference.py` /
`tools/verify_states.py` 刻意共享仪器，"Nothing here trusts numbers reported by the implementer"）。

**可接受**：是——但**必须先承认这个噪声底**：任何小于 0.5 uu 的差异都不该被当成实现错误。
这也是本移植把验收线定在 `|Δ| ≤ 0.2°`（角度）而不是"逐像素相同"的原因。

## ④ 本机 `Mbps` 的 advance 比 Chromium 宽 1.25 uu

**现象**：单位行是 `[图标 16] + gap 4 + "Mbps" @14`，本机排出来整行比参考**宽**。

**量化影响**：

- Chromium 合成宽度：`2.866 em × 14 = **40.12 uu**`（`docs/visual-targets.md` §3 实测推进）。
- 本机（skrifa @14，无 subpixel）实测：**41.37 uu** ⇒ **+1.25 uu（+3.1%）**。
- 该 +1.25 uu 会让整条单位行在"居中"约束下**左右各挤出 ~0.6 uu**，并让 `Mbps` 的右边界越过
  参考的 170.0 uu 锚点。

**根因机制**：与 ① 同源（14 ppem 的整数字形推进），但这里影响的是**整行的水平居中**，
所以视觉上比单个刻度数字更明显。

**已尝试的修复与结果**：

1. 改字体 → 只有 Gauge Mono / Montserrat 两个合法选项，都不换；
2. 逐字 `letter-spacing` 负值 → Slint 支持 `letter-spacing`，但会让字形本身重叠，且不同 DPR 下
   取整不同，放弃；
3. 采用 `unit-row-dx = -1.25`（`ui/speed-gauge.slint:94,97`）：把整行左移，**用位移吃掉宽度差**。
   这是"补偿"而不是"修正"——宽度差还在，只是锚点回到了参考位置。

**可接受**：是。位移后 `Mbps` 右边界回到 170.0 uu 附近，读数可读性与对齐不受影响；
`+1.25 uu` 已在 README 与本节显式披露。

## ⑤ 抗锯齿算法差异导致的边缘像素

**现象**：本移植与参考图在**边缘一像素**上不可能逐点相同。

**量化影响**：

- 亮弧终点（sweep end）偏差：`+0.10 / −0.06 / +0.03 / −0.14 / −0.05°`（5 个可测状态），
  换算到 1144 图上是 `±1.3 px`（`docs/visual-targets.md` §6）。
- 圆环内外半径读数散布见 ③（0.5 uu）。
- 笔画粗细：参考图里"暗字亮底 vs 亮字暗底"的 sRGB 抗锯齿合成方向不同，肉眼能看到 1 px 级差异
  （`docs/reference-inventory.md` §3 对 `compare-numbers.png` 的说明）。

**根因机制**：Chromium 用 Skia 的 analytic AA（覆盖率由几何精确积分）+ LCD/gamma 校正；
Slint 的 femtovg 走 MSAA/覆盖率缓冲，software 后端走 tiny-skia 的 4× 超采样。三者对
"半个像素覆盖"给出的灰度值不同 ⇒ 边缘像素必然有 ±几级的差。

**已尝试的修复与结果**：

1. 试过在 `.slint` 里给 `Path` 加 0.25 px 的描边"加粗" → 环宽从 23.0 变 23.5，反而超出验收线；
2. 试过提高渲染倍率（DPR 4 输出 1144）→ 边缘更清楚但**差值不消失**（只是把 1 px 摊到 4 px）；
3. 结论：把验收线写成**角度/半径**这类几何量（抗锯齿不变），而不是逐像素相等。

**可接受**：是。这是渲染器替换的**固有代价**，不是缺陷；已用几何量验收线兜住。

## ⑥ 指针渐变：从"32 片切片"到"整条光栅化"的四轮迭代

这是本移植最长的一条坑，四轮都被反证过，最终方案不是"更聪明"，而是**换了一条不共享边的路**。

### 6.1 现象

原实现是**一条 SVG path + `linearGradient`**（上端 60% 白 → 下端透明）。但 Slint 软件渲染器画
`Path.fill` 时**只取 `Brush::color()`**（`i-slint-renderer-software-1.18.1/lib.rs:3022-3030`），
渐变画刷的 `color()` 是**透明** ⇒ 整条指针直接消失。

### 6.2 四轮迭代与实测数字

| 轮次 | 方案 | 机理 | 实测最大偏差（沿轴剖面 / 255） | 结论 |
|---|---|---|---:|---|
| 1 | **alpha 切片**（32 片梯形、严格共边、逐片 `over`） | 共享边上的像素被相邻两片各覆盖 `c` / `1−c`，合成两次后覆盖不足：`−a²·c(1−c)·255` | **21** | 接缝肉眼可见 |
| 2 | **不透明预合成**（`SliceComposite::Opaque`） | 把 `a²` 换成 `a`，误差从 `a²c(1−c)` 变成 `a·c(1−c)`，量纲上**放大 `1/a`** | **36**（light 主题 **+45.9**） | 更差，放弃 |
| 3 | **重叠补偿**（每片向外多伸 0.35 uu） | 片体不再共边，但 `over` 顺序变成"内→外"，重叠区里后画的片把前一片**再压一次** ⇒ 接缝搬进片体内部 | **60**（指针 `mean|Δ|` 1.72 → 33.88，全图 `mean|Δ|` 0.579 → 0.966） | 更差，放弃 |
| 4 | **整条光栅化**（tiny-skia 画一张 RGBA → Slint `Image` 一次合成） | 每个像素**只被 alpha 混合一次** ⇒ 上述 `c(1−c)` 项恒等于 0 | **1.00** | 采用（阈值 4/255） |

### 6.3 代数式（为什么前三条路都必败）

设某像素被第 `i` 片覆盖的覆盖率为 `c_i`、该片的颜色/alpha 为 `A_i`，软件渲染器按 painter 顺序
逐路径做 `over`。两条严格共边的路径在边界上必有 `c_i + c_{i+1} = 1`：

```
理想：  C = A·c + 0·(1−c)              （一次混合）
实际：  C' = A·c_{i+1} + (A·c_i)(1−c_{i+1})
        = A·[c_{i+1} + c_i(1−c_{i+1})]
        = A·[c_{i+1} + (1−c_{i+1})(1−c_{i+1})]
丢掉的量：A·c(1−c)                       （c = 0.5 时最坏 ⇒ 0.25·A）
```

- 把 `A` 换成局部 alpha `a` ⇒ 误差 `a²c(1−c)` ⇒ 第 1 轮（dark 实测 21/255）；
- 反过来把片做成**不透明**（`a = 1`）⇒ 误差退化成 `c(1−c)·(P − C_i)`，`P` 是页面色、`C_i` 是片色，
  在 light 主题下 `P − C_i` 巨大 ⇒ `+45.9`（第 2 轮）；
- 加 overlap 只改变"哪两个片在争这个像素"，`c(1−c)` 项**依然存在**，而且重叠区里第三次混合让它
  更糟 ⇒ 60（第 3 轮）；
- 只有"每像素只混合一次"才能让 `c(1−c)` 项**恒为 0** ⇒ 1.00（第 4 轮）。

**片数扫描的旁证**：`N ∈ {32, 64, 96, 128, 192}` 的 `max|Δ|` = `9 / 19 / 22 / 19 / 23`（都 ≥ 9）——
因为这几个 N 都是 32 的倍数，只是把已有接缝保留下来再插新接缝，接缝数随 N 单调上升。
**加片数解决不了问题**，这直接否掉了"再切细一点"的直觉。

### 6.4 代价与开关

- 常驻内存：DPR1 / 572 逻辑 px 时 **0.88 MiB**（`Pixmap` + 输出 `Vec` 双缓冲），DPR4 时 **14.11 MiB**
  （见 `docs/performance.md` §6.3）。
- 每帧 CPU：光栅化 + 上传 ~462 KB（DPR1）；`bench` 里指针"生成"占 0.07 ms（286²）/ 0.33 ms（572²）。
- 稳态零分配：画布只在像素边长变化时重建，`needle_raster_resizes()` 预热后恒为 1。
- **可以关掉**：`--no-default-features --features desktop,bundled-fonts,screenshots`（即去掉
  `needle-raster`）就退回 32 片平色路径——两条路都能编译、都能测，只是接缝回来。

**可接受**：是（1.00/255 ≪ 阈值 4/255）。这是本移植唯一"必须换实现手段"的地方。

## ⑦ 单连接强调色未经像素校准

**现象**：4 组强调色里，`download` / `upload`（多连接）是**像素实测**过的，`downloadSingle` /
`uploadSingle` 不是。

**量化影响**：

| 强调色 | 值 | 校准状态 |
|---|---|---|
| `download`（multi） | `#00c5bd`（实测 `rgb(0,197,189)`） | 已校准（原矩阵近似 `#00c9c0` 差 4 级，已改用实测） |
| `upload`（multi） | `#b45aed`（实测 `rgb(180,90,237)`） | 已校准（近似 `#b75cf0` 差 3 级） |
| `downloadSingle` | `#e56b4f` | **未校准**（保留源码声明值） |
| `uploadSingle` | `#7cdb2b` | **未校准** |

**根因机制**：参考截图集**只覆盖多连接状态**（`src/model.rs` 注释原话："参考截图只覆盖多连接
状态（单连接强调色没出现在 8 张验收图里）"），单连接没有可比对的像素，无从实测。

**已尝试的修复与结果**：

1. 用 P3→sRGB 矩阵换算 —— 恰恰是 ⑦ 里被实测否掉的方法（多连接那两组就是矩阵近似错了 3–4 级），
   所以不能对单连接再犯同样的错；
2. 拿原站线上抓包 —— 超出本仓库范围（`comparison/` 里的 `reference-live-*.png` 只能人工目检）；
3. 现状：**保留源码声明值，不做任何矩阵/经验修正**（这也是 `model.rs` 里写明的策略）。

**可接受**：是（有条件）。潜在偏差量级参考多连接那两组 = 3–4/255 色阶，肉眼近似；但**未经实测**
这一事实已在 `README`、`module-map.md` D3 与本节三处披露。

## ⑧ light 主题没有官方参考图

**现象**：`GaugeTheme::Light` 的配色无法与参考图逐像素对拍。

**量化影响**：`comparison/ref-metrics/*.json`（6 份）全部是 dark 主题口径，没有任何 light 参考；
因此 light 主题下：

- `page` 用 `#f2f2f2`（照抄 `styles.css`），而原站实测是 `color(display-p3 0.949 0.95 0.949)`
  ⇒ 在 P3 屏上**不等价**（`docs/port-spec.md` 附录 B8 明确写"浅色主题的页面底色是'近似'，
  不是精确复刻"）；
- 指针渐变（light 版 `#ffffff → #a4a4a4(58%) → #222222`）与原站一致，但**无像素验收**；
- 轨道色 `#e2e2e2`、刻度 on/off `#000000` / `#a3a3a3` 同属"按 token 实现、无参考图"。

**根因机制**：参考截图是原站在 **dark** 页面下拍的；light 主题在原站是 CSS 变量切换，
原作者没有留下对应的 1144 截图。

**已尝试的修复与结果**：把 light 的每个 token 都对着 `styles.css` 的可读值抄（`port-spec.md`
§11 有完整 CSS 变量表），并把 `page` 的 P3 差异写进附录 B8 而不是"偷偷用矩阵换算"。

**可接受**：是（有条件）。dark 主题可逐像素验收，light 主题只能保证"token 与 CSS 一致"。

## ⑨ `gigabit` 无参考图（`extended` 有）

**现象**：8 张状态图里，`gigabit`（`static=1000&stage=download`）在参考侧**没有对应文件**。

**量化影响**（`docs/reference-inventory.md` §2.4 / §2.5）：

| 状态 | 有参考图？ | 说明 |
|---|---|---|
| `idle` / `low` / `mid` / `high` / `upload` / `done` | ✅ | `report/local-*.png`，1144×1144 |
| `extended`（`static=4200&scale=auto`，10 档） | ✅ | `report/local-extended.png` |
| **`gigabit`（`static=1000&stage=download`）** | ❌ | 只在 `shots/` 口径（912×912）里存在，`report/` 里没有 |

`gigabit` 是 **9 档量程的最右端**（1000 Mbps = +135°），也是唯一"满弧 + 全部刻度点亮 + 数字
`1,000.00` 塞满中央"的状态，理论上最容易暴露布局问题。

**根因机制**：原作者的截图脚本（`tools/artifacts.mjs`）只拍了 7 个 report 状态；`gigabit`
是后来 `tools/shoot.mjs` 加进 `shots/` 的，没有进 `report/`。

**已尝试的修复与结果**：本移植仍然生成 `comparison/render/gigabit.png`（1144×1144），并做了
**间接验收**：`gigabit` 与 `high` 共用同一套几何（只差亮弧长度与点亮数），而 `high` 有参考图；
角度由 `scale.rs` 的插值公式保证（1000 → +135.000°），公式本身有黄金向量测试。
另有一条免费断言：`done ≡ high` 逐字节相同（`docs/visual-targets.md` §7）。

**可接受**：是（有条件）。`gigabit` 的**数值/角度**可验证，**像素级配色**只能靠同变体类推。

## ⑩ `ComponentContainer` / `component-factory` 属 Slint experimental（仅 Demo 使用）

**现象**：Demo 要把"Rust 侧创建的仪表实例"塞进 `.slint` 的自定义布局，而这在 Slint 1.18 里只有
`ComponentContainer` + `component-factory` 一条路，且它们是 **experimental** 元素。

**量化影响**：

- 需要在 `build.rs` 里**就地置位** `SLINT_ENABLE_EXPERIMENTAL_FEATURES` 才能编译（`build.rs:5-9`）；
- 该 API 在 Slint minor 升级时**可能不兼容**（`ComponentFactory` 的类型签名、`component-factory`
  属性的类型都属 experimental 区域）；
- 影响面：**只有 `ui/demo.slint` + `examples/demo.rs`**。`ui/speed-gauge.slint` 与 `src/gauge.rs`
  完全不依赖它 ⇒ 组件库本身不受这条限制。

**根因机制**：Slint 的属性类型系统里没有"组件实例"类型
（`i-slint-compiler::expression_tree::Type` 无 Component 变体，生成代码只给属性/回调生成访问器），
所以"Rust 拿到实例 + `.slint` 自定义布局"只能走 ComponentFactory 闭包：闭包里把创建出来的
`SpeedGauge` 存进 `Shared`，Rust 于是能 `GaugeHandle::attach` 它。

**已尝试的修复与结果**：

1. 想在 `.slint` 里直接 `SpeedGauge { }` 声明 —— 那样实例归 `.slint` 所有，Rust 侧拿不到
   （除非再走 `#[global]` 或属性桥），且同一个 `.slint` 被独立编译两次会产生**两个不同的 Rust
   枚举类型**（Demo 里 `GaugeStage ≠ speed_gauge_slint::GaugeStage`），因此 Demo 改用中性
   `int`/`bool` 传状态；
2. 想用 `@children` 或 `ComponentFactory` 之外的回调 —— 都不传递实例；
3. 现状：Demo 接受 experimental；**下游集成有替代方案**：要么在 Rust 里 `SpeedGauge::new()` 直接
   用（§README 3.2，不需要 experimental），要么在**自己的** `.slint` 里 `import { SpeedGauge }`
   声明（由你自己的 `build.rs` 编译），此时实例归你的 crate 所有、也不需要 experimental。

**可接受**：是（有条件）。风险被**限制在 Demo 层**，且已在 README 与 `module-map.md` D11 标注；
升级 Slint 时若该 API 变更，只有 `ui/demo.slint` + `examples/demo.rs` 需要跟着改。

## ⑪ 文字落点被量化到整像素 ⇒ 非整数缩放时"尺寸不变性"有上界

**现象**：环、指针、sweep 角、刻度 x 这些**矢量量**在 286/300/440/640 四档缩放后归一化完全一致
（≤0.169 uu），但**由文字推导的量**会漂：单位行 ink 中心 x 最大 **0.944 uu**、刻度中心 y **0.686 uu**、
数字 ink 中心 y **0.405 uu**（`comparison/report/invariance.md`，判据 ±0.4 uu）。

**量化影响**：0.944 uu = **3.8 px @1144**，只在逻辑尺寸不是 286 整数倍时出现。
DPR 档（572 @DPR1/2/3，k 恒为 2）最大只有 **0.250 uu**，不受影响。

**根因机制**：Slint 的文字排版把字形落点对齐到整**逻辑**像素（不是物理像素），
所以 ink 位置有 ±0.5 逻辑像素的量化，归一化成 uu 后就是 ±0.5/k uu —— k≈1.05（300px）时约 0.48 uu，
两个方向叠加即 0.94 uu。证据不是推理：数字字形的纵向尺度 σy 与 `floor(36k)/k` 的预测比在四个采样点上
一致到 0.15% 以内（286 1.0000/1.0000、300 0.9798/0.9792、440 0.9931/0.9916、640 0.9931/0.9924），
说明**字号本身也被向下取整**了。

**已尝试的修复与结果**：

1. 想在 `.slint` 里改字号表达避免取整 —— 字号是 `length`，最终仍走同一条物理像素换算路径，无效；
2. 让文字也走"路径光栅化"（像指针那样）—— 可以拿到矢量级缩放，但会失去字体回退、kerning 与
   HiDPI 的原生文字质量，代价远大于收益，**未采用**；
3. 现状：**不做补偿**。把"矢量量"与"文字量"分开报（`invariance.md` 里两栏），
   并把这条写成上界：**矢量量 ≤0.2 uu；文字量 ≤1.0 uu（逻辑尺寸非 286 整数倍时）**。

**可接受**：是。参考图对拍的标定口径是 **572 CSS @DPR2**（k=2，整数倍），该口径下文字量偏差
≤0.75 uu；非整数缩放只会让文字整体缩 0.7%（肉眼不可辨），不影响任何几何对齐结论。

## ⑫ 未点亮的轨道比参考"窄"约 0.3 uu

**现象**：idle / low 这类**没有亮弧**的状态，我们的轨道环带比参考窄：能量法 Δinner **+0.295 uu**、
Δwidth **−0.191 uu**；而有点亮的状态几乎为零（Δinner −0.004、Δwidth +0.064）。

**量化影响**：1.2 px @1144，仅出现在暗轨道段。

**根因机制**：参考实现里"轨道弧"与"彩弧"是两条独立的 `stroke`，浏览器对两者的
抗锯齿覆盖曲线不完全相同（外缘几乎同位置、内缘向内多覆盖约 0.3 uu）；我们的实现里两者用同一
几何与同一 `stroke-width: 23px*k`，因此与**彩弧**对齐、与**暗轨道**差 0.3 uu。这是取其一的结果。

**已尝试的修复与结果**：可以把轨道 `stroke-width` 加到 23.4 uu 去贴合暗轨道读数，
但那会让亮弧与轨道在交界处（如 mid/high 的弧头）出现 0.4 uu 的台阶，**反而更差**，未采用。

**可接受**：是。0.3 uu 小于抗锯齿过渡带宽度（1 px 逻辑 ≈ 0.5 uu @k=2）。

## ⑬ 量测仪器的阈值口径本身会带 0.5 uu 的假偏差

**现象**：同一对图，`tools/measure_reference.py` 的 `luma>8` 阈值扫描给出 Δinner **+0.50 uu**，
而覆盖率能量积分给出 **−0.004 uu**。也就是说 `comparison/ref-metrics/*.json` 里
118.3…118.8 那 0.5 uu 的散布里，有相当一部分是**尺子**而不是几何。

**量化影响**：只影响报告数字，不影响渲染。

**根因机制**：阈值法测的是"第一个越过阈值的像素"，量化步长 = 1/scale uu（0.45–1.0 uu），
天然大于判据 ±0.4；能量积分测的是覆盖率重心，可跨分辨率比较。

**处理**：既有的 `ref-metrics/*.json` **保持原样**（它是历史基线，改了会污染对拍链）；
`tools/compare_report.py` 里**两种口径并列**，`tools/invariance.py` 与 `tests/visual.rs` 用能量法，
并在 `comparison/report/summary.md` 与 `invariance.md` 里写明为什么。

**可接受**：是。两把尺子并列比"偷偷换一把更宽松的"诚实。
